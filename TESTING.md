| **Node distributed simulation** | `node tests/test_distributed_inference.js` and `node tests/test_stage5_pipeline.js` | PASS (Test D; Stage 5: 50 of 50), run 2026-11-14 | `PipelineA` + `PipelineB` with real partitions over an in-memory channel: chunking at 16 KiB / 64 KiB / 256 KiB limits, a 512-token activation, session/seq matching, duplicate refusal, corruption and failure handling, logits vs PyTorch within 1e-5 and identical to local inference | Real DataChannel behaviour; browser JS engines |

### Numbers measured on 2026-11-14 (torch 2.15, Node 22, headless Chromium)
- JS engine vs PyTorch, per reference case (6 cases, T = 1..200): activation difference <= 1.07e-6, logits difference <= 1.13e-6, same argmax byte in all 6. Tolerance is 1e-5. **JS and PyTorch are not bit-identical**; they agree to about 1e-6.
- Distributed (A -> channel -> B) logits are **bit-identical to calling the same JS engines directly** (the transfer loses nothing). That is a JS-vs-JS statement.
- Real DataChannel in the two-tab run: negotiated `pc.sctp.maxMessageSize` = 262144. A T=200 activation (307,248 bytes) was sent as 2 frames; smaller ones as 1 frame.
- A normal UI run from the prompt "MESH" generated 24 bytes through the two tabs; the text equals the Node `MeshFullModel` greedy output for the same prompt.

### What the console helper does (`Frontend/stage5-test.js`)
`meshStage5.validate()` runs two groups and prints PASS / FAIL / SKIP per check. SKIP means the check was **not run** (for example no peer is connected), and a SKIP is never counted as a pass.
- **LOCAL** (needs no peer): weights Adler-32 + size, rejection of a flipped byte / short file / manifest without checksums, fixture checksums = manifest checksums, model fingerprint, A's activation and B's logits vs PyTorch, tensor-packet round trip, tensor validation (NaN, wrong rank, wrong hidden size, wrong dtype, corrupted bytes), in-memory pipeline runs with chunking, wrong-fingerprint / duplicate / stray-reply handling.
- **TWO-DEVICE** (needs a connected peer): pipeline initialised, HELLO verified, negotiated limit, a real A -> B -> A round trip for each reference case compared with PyTorch, and B refusing a NaN activation and a corrupted packet sent over the real channel. Check "real transfer" and "B rejects" only run on Device A.

### Other scenarios checked with scripted headless Chromium (2026-11-14)
- DataChannel opens **before** B's weights finish loading (download delayed 6 s): A's HELLO is queued on B, the pipeline is created once after the load, both sides verify, inference works.
- B is served a tampered `partition_b.bin`: B shows "Weights REJECTED: partition b checksum ... does not match manifest ...", builds no engine and no pipeline; A's request fails with "no HELLO received from Device B" (after its timeout).
- The DataChannel closes while A is waiting for a reply: A's request fails immediately with `CHANNEL_CLOSED` instead of waiting out the timeout.

### Manual test steps (you)
1. `python model/export_weights.py && python model/export_stage5_reference.py` (needs PyTorch).
2. `cd room-server && npm install && npm start`, then open `http://localhost:3000`.
3. Tab 1: *Find my other half* -> *Create room*. Tab 2 (a new tab or a second device on the same network, using `http://<computer-ip>:3000`): *Join room* with the code.
4. Wait for "Connection successful" on both. Open DevTools (F12) -> Console on **tab 1 (Device A)**: `await meshStage5.validate()`. Run `await meshStage5.twoDevice()` on tab 2 as well (it reports Device B's connection checks and SKIPs the checks only A can run).
5. Enter the workspace on Device A, Inference tab, type a prompt, *Run inference*.
6. Physical devices: repeat steps 2-5 with two phones/computers. Both devices must be able to reach `http://<computer-ip>:3000` (same network). The only STUN server configured is Google's public one; there is no TURN server, so two devices behind strict NATs may fail to connect.

## 6. Stage 6 — reliability tests
